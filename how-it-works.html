How PixelForge works

A practical explanation for using and demonstrating the deployed Studio.

1. What you are opening

The public site combines a visual game creator and playable game library, with a separate full cartridge Studio. It runs the supplied C/C++ runtime compiled to WebAssembly with Emscripten. You can edit code, sprites, tile maps, sound effects and music, then run a cartridge in the same environment.

The Go visual creator is the home-page editing experience. Its scene JSON and .pforge project formats are different from this Studio’s .pf cartridges. The two interfaces are separate implementations, not interchangeable file formats.

Game script + graphics + audio→ .pf cartridge→ PixelForge runtime→ Display, input and sound

2. The public deployment

GitHub Pages serves this page, JavaScript, the WebAssembly runtime and demo cartridges over HTTPS. A visitor’s browser downloads them and runs the Studio locally. Your laptop and Docker do not need to stay running for this public website. First launch needs an internet connection; this is not a guaranteed offline app.

The .sh launcher is a convenience menu on a development computer. Docker is another way to build or serve the browser edition locally. Neither the shell script nor Docker runs inside GitHub Pages.

3. Open any included game

Open Studio, click the launch button and wait. In its console type:

ls
load fire
run

There are 35 supplied cartridges, including Tetris, Fire, Terrain, P3D, Quest, Brickbreaker, Emptyhouse, Rooms and Pac-Man. These are examples and tests of the runtime; not every cartridge is a finished game. The language-specific benchmark cartridges need their corresponding embedded language runtime.

Esc leaves the running game. Load another cartridge and run it. Save a copy before editing: save supervisor-demo.pf.

Use Ctrl+R to run and Ctrl+S to save. On a Mac, Fn may be needed for function keys. The visible menus provide the same navigation.

5. The game loop and API

For a Lua cartridge, function PF() is the main per-frame callback. The runtime repeatedly calls it. A script reads input, changes its state and draws the new result. The legacy TIC callback is also accepted by this supplied runtime.

function PF()
  cls(0)
  print("Hello from PixelForge", 20, 20, 12)
end

cls clears the display; btn reads held buttons; btnp reads press events; spr draws sprites; map draws tiles; sfx and music play cartridge audio. These are scripting API functions, not REST endpoints.

Developers make new .pf games by creating a cartridge, writing a script against those APIs, authoring assets, testing and saving. A map editor does not automatically give every game collision rules: the script/runtime must implement those rules. Rooms, for example, uses tile flags to identify walls.

6. Files and saving

The .pf file is a cartridge containing game code and assets. At startup this host installs supplied example cartridges after restoring browser storage; it does not overwrite existing saved copies with the same name. Browser storage uses IndexedDB. Each browser/device has its own copy; clearing site data can remove it.

Saving inside Studio is not a GitHub commit and does not publish a visitor’s game. Download/export your cartridge to keep a portable copy, or use the Studio’s import/upload controls to bring one in. Browser storage and your computer’s native Studio folder are separate.

7. Sharing and export

Anyone with the public link can open the deployed Studio. HTML export uses the supplied browser template. This host routes its template requests under the GitHub project’s directory. Native platform export templates are not supplied here, so Windows/Linux/Mac executable export must be prepared and tested separately. The developer’s recording showed a native export download failure; deployment does not by itself fix that missing-template path.

This is static browser hosting. It does not add user accounts, a server database, public game-upload hosting, multiplayer or video streaming. Editing is most practical with a desktop keyboard. Physical phone input and performance need separate testing.

8. A ten-minute supervisor demo

  1. Open this public URL to prove the deployment is accessible without localhost.
  2. Use ls, then load and run two different examples.
  3. Stop and show the code callback and three API calls you understand.
  4. Save a copy; edit a visible sprite, run again and point to the change.
  5. Show the map, sound-effect and music editors.
  6. Save and reopen your copy. Show capture with F8 or GIF start/stop with F9 if rehearsed.
  7. Explain the difference between a cartridge, runtime and hosting. Describe any untested export/device features accurately.

What to say

“This is our deployed browser Studio. GitHub Pages delivers the runtime and cartridges; WebAssembly runs the Studio in the visitor’s browser. The .pf cartridge holds the game’s script and assets. I can load a game, edit its code or graphics, run the change and save a new cartridge.”

Describe the existing engine base, third-party libraries and your own verified contributions separately. The source repository includes earlier Go work; the supplied cartridge Studio uses the C/C++ architecture described here.
