# Pixelforge: A From-Scratch 2D Pixel Game Engine in Go

Most game developers today reach for Unity or Unreal Engine without much thought. Those tools are powerful, but they also bury you in abstraction, pull in enormous dependency trees, and make it genuinely hard to see what is actually happening when a pixel gets drawn. For 2D projects especially, all that machinery feels disproportionate. Meanwhile, Go has carved out a reputation in servers, CLI tools, and infrastructure work, but nobody really talks about it for games. The ecosystem simply is not there yet.

That gap, between what exists and what a clean, learnable game engine in Go could look like, is exactly what Pixelforge tackles. It is a complete 2D game engine written in Go from scratch: rendering, input, audio, an event system, and developer tools all built from the ground up. It runs at 320 by 180 pixels with a 64 colour palette, deliberately constrained to keep the scope focused. The code is split across 14 packages, each testable in isolation, and every hot path runs with zero heap allocations. Getting all of those properties together in a garbage collected language is genuinely difficult, and worth talking about.

The rendering pipeline is where most of the real-time work happens. Every pixel operation, setting individual pixels, drawing lines and circles, compositing sprites onto a canvas, runs on the CPU through direct memory access. There is no GPU involved, no shaders, no driver calls. The line drawing uses Bresenham algorithm, which sidesteps floating point arithmetic entirely by keeping an error accumulator and advancing one coordinate at a time. Circles use the midpoint algorithm with octant symmetry to cut the iteration count roughly in half. Sprite stretching precomputes stride values so it can jump directly to any pixel via flat indexing, bypassing any per pixel function call overhead. Colour table lookups, which handle transparency and palette remapping, run in constant time through a precomputed four entry table keyed on the most significant bits of the source and destination colour indices. At 60 FPS on a 320 by 180 canvas, the engine is moving about 3.46 million pixels per second. Benchmarks show filled rectangles clearing in 11.9 microseconds and a full canvas wipe in 26 microseconds, both comfortably inside the 16.67 millisecond frame budget, leaving real headroom for everything else.

The event system is where things get interesting from a systems design perspective. Most Go implementations of the observer pattern lean on interface values, which forces a heap allocation whenever a concrete value is stored inside the interface. Pixelforge takes a different approach: Target is a plain struct holding a slice of typed function closures, and Publish dispatches directly to each handler with no interface boxing anywhere in the call chain. The benchmark reads 18.76 nanoseconds per publish with zero allocations. That is fast enough to live entirely in L1 cache on any modern CPU. At 60 FPS, if even one heap allocation snuck into the event path per frame, you would accumulate about 1,800 allocations per second, enough to kick the garbage collector into action and introduce visible frame hitches. The current design avoids that entirely.

The audio mixer emulates the four channel architecture of the Amiga Paula chip. Each channel runs its own PCM sample stream independently, with its own pitch, volume, and loop settings. Channels 0 and 3 pan left; channels 1 and 2 pan right. At 44.1 kHz stereo, the mixer is producing 88,200 output samples per second, and each one may require fetching from up to four sources, scaling by volume, and accumulating with clipping. The command scheduler commits audio parameter changes to a ring buffer so that pitch and volume adjustments land sample accurately without blocking the game loop. That same ring buffer structure shows up again in the piscope frame debugger, where it stores screen snapshots for backward navigation through frame history, which turns out to be surprisingly useful when a bug only manifests for a couple of frames during fast gameplay.

Beyond the event system, memory discipline runs through the whole engine. Surface keeps pixels in a flat contiguous slice, so there is no pointer chasing during pixel access. The LinesIterator uses Go 1.23 iter.Seq2 protocol to walk the canvas row by row without allocating any intermediate collections. The object pool hands out pre allocated buffers and takes them back when done. None of these are revolutionary ideas, but applying them consistently across every hot path means the garbage collector essentially never intrudes on the game loop, which for a real time interactive application matters more than raw throughput numbers.

piscope, the built in debugging overlay, is worth mentioning separately. It runs entirely in Go, without any C bindings or OS specific syscalls, and gives you frame stepping, CPU and memory monitoring, and screenshot capture directly inside the game window. The frame recorder stores each rendered frame in the ring buffer, so you can step backwards to see exactly what the screen looked like three frames ago. That kind of tooling usually requires hooking into an external profiler; having it embedded in the engine itself is genuinely useful during development.

The test suite has 43 automated tests across 14 packages, all passing. There are 15 benchmark suites covering every measured subsystem. Integration examples demonstrate the engine handling minimal games, interactive shape drawing, Snake with keyboard and gamepad input, piano playback, GUI buttons, and more. This is not a prototype that works in a toy scenario; it is a working engine you could ship a game with.

The takeaway is straightforward: Go can do real time interactive work at 60 FPS if you design for it. Getting there requires paying attention to where allocations actually happen, choosing data structures that stay cache friendly, and being deliberate about avoiding interface types in hot paths. The problems Pixelforge tackles, raster graphics, zero allocation event dispatch, audio signal processing, concurrent ring buffers, are not simple, but they are solvable, and this codebase shows how.
